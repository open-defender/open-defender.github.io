快速开始

Open Defender 在使用 systemd 的 Linux 系统上运行。可以从 GitHub Releases 手动下载对应架构的二进制文件，也可以用以下命令自动识别架构并将文件安装到 /usr/bin/open-defender。

(
  ARCH=$(uname -m)
  case "$ARCH" in
    x86_64)        ARCH=amd64 ;;
    i386|i686)     ARCH=386 ;;
    aarch64|arm64) ARCH=arm64 ;;
    armv7l)        ARCH=arm32 ;;
    *) echo "不支持的系统架构: $ARCH"; exit 1 ;;
  esac
  sudo curl -fL -o /usr/bin/open-defender \
    "https://github.com/fridalif/open-defender/releases/latest/download/open-defender_$ARCH" &&
    sudo chmod +x /usr/bin/open-defender
)

安装并启动服务，验证配置，然后查看已启用的监控模块。

sudo open-defender -i
open-defender -t
open-defender -s

服务管理

使用 systemd 查看服务状态、重启服务或持续查看日志。也可以用 sudo open-defender -r 重启服务。

systemctl status open-defender
sudo systemctl restart open-defender
journalctl -u open-defender -f

配置

代理的配置文件为 /etc/open-defender/config.yaml。可以为各个监控模块设置事件来源和触发阈值。

监控模式

  • blocker 检测事件并执行配置的阻止规则。
  • logger 记录匹配的事件，允许相关活动继续。
  • disabled 关闭该监控模块。

主要配置项

  • engine 选择事件来源，可设为 syslog、journal 或 docker。
  • log_path 指定 syslog 文件。systemd journal 或 Docker 来源使用 unit_name。
  • pattern 是带有 (?P<ip>...) 命名分组的正则表达式。
  • tries、window_seconds 和 ban_seconds 分别设置触发阈值、观察时段和封禁时长。
  • ip_whitelist 指定不会被封禁的地址。
  • resource_monitor 可为 CPU 和内存配置 warning 和 alert 阈值。阈值设为零时关闭对应检查。
sudo nano /etc/open-defender/config.yaml

修改后运行 open-defender -t。该命令读取配置并报告校验错误，不会修改文件。

监控模块

open-defender -s 会显示启用的模块、模式、日志引擎、来源和阈值。关闭的模块会列在表格下方。

/etc/open-defender/config.yaml

MONITOR           MODE     ENGINE   SOURCE                   TRIES
ssh_monitor       blocker  syslog   /var/log/auth.log        5 in 300s, ban 900s
database_monitor  logger   journal  postgresql               5 in 300s
resource_monitor  enabled  -        /var/log/open-defender/  cpu 60/90, ram 60/90

disabled: web_recon_monitor, web_brute_monitor
ssh_monitor
通过认证日志检测 SSH 暴力破解。
web_recon_monitor
检测针对 Web 应用的探测行为。
web_brute_monitor
检测针对 Web 应用的暴力破解。
database_monitor
通过 syslog、journal 或 Docker 日志检测数据库暴力破解。
resource_monitor
监控 CPU 和内存，在过载时列出资源占用最高的进程。
network_antirecon
使用 eBPF 检测 TCP 和 UDP 端口扫描。
user_command_controller
通过 BPF LSM 观察或阻止命令执行。

网络反探测

ebpf_monitors.network_antirecon 通过 eBPF 和 XDP 检测 TCP、UDP 端口扫描。访问拒绝列表中的端口会立即触发事件。模块也会统计同一来源 IP 在观察时段内访问的不同端口数量。

ebpf_monitors:
  network_antirecon:
    mode: logger
    ports_count: 10
    window_seconds: 300
    ban_seconds: 900
    whitelist_ports: [22, 80, 443]
    blacklist_ports: []

ports_count 是不同端口数的阈值。设为零可关闭这项检查。whitelist_ports 的优先级高于 blacklist_ports。在 blocker 模式下，来源 IP 会被封禁 ban_seconds 秒。修改后校验配置并重启服务。可先用 logger 查看规则匹配了哪些流量。

命令执行控制

ebpf_monitors.user_command_controller 通过 BPF LSM 检查可执行文件的启动请求。此模块需要 BTF、已启用的 BPF LSM，以及在宿主机初始用户命名空间中以 root 运行的代理。挂载或更新失败时，代理会记录错误并停用控制器，其余模块继续运行。

以下示例记录 UID 为 1000 的用户尝试运行 curl 或 wget 的事件。

ebpf_monitors:
  user_command_controller:
    mode: logger
    block_type: positive
    target_users_ids: ["1000"]
    target_commands: ["curl", "wget"]
  • 选择 disabled 或省略该配置节都会关闭控制器。logger 允许匹配的请求并发出 Critical (4) 事件。blocker 会以 EPERM 拒绝请求并发出 High (3) 事件。
  • target_users_ids 使用进程所属用户命名空间中的 UID。target_commands 匹配可执行文件的基本名称，最长 63 字节。模块不跟踪无需启动独立可执行文件的 shell 内置命令。
  • 两个列表均有内容时，用户和命令都必须匹配。单个列表为空时，对应条件不受限制。两个列表均为空时，没有匹配项。
  • block_type: positive 选择匹配项。negative 选择其余请求，同时遵守控制器的排除规则。

真实或有效 UID 为 0 的进程始终被排除，包括宿主机和容器用户命名空间中的 root。日志事件仅表示一次执行尝试。

未知的用户或挂载命名空间中的执行请求会直接放行，并且不会生成事件。代理在挂载控制器之前发现命名空间，之后每 150 秒再次扫描，每个新发现的命名空间还有 150 秒准备时间。两个命名空间都就绪后才应用策略。

校验配置，重启服务，然后检查日志。

open-defender -t
sudo open-defender -r
journalctl -u open-defender -f

通过 GRUB 启用 BPF LSM

先检查内核是否支持 BPF LSM，以及它是否已经启用。如果 LSM 文件不存在，可能是 securityfs 未挂载，或系统无法提供 LSM 信息。

cat /sys/kernel/security/lsm
cat /proc/cmdline
grep CONFIG_BPF_LSM /boot/config-$(uname -r)

已启用的列表中如果包含 bpf，就无需修改 GRUB。内核需要启用 CONFIG_BPF_LSM=y。若系统将内核配置保存在其他位置，请按发行版的说明检查。

备份 GRUB 配置，并确认可以访问恢复控制台。检查 /etc/default/grub 和 /etc/default/grub.d/。如果已有 lsm= 参数，将 bpf 追加到现有列表。否则，将 /sys/kernel/security/lsm 中的列表与 bpf 一起写入 GRUB_CMDLINE_LINUX 中的一个 lsm= 参数。保留其余内核参数。

例如，当前列表为 lockdown,yama,integrity,apparmor 且该变量没有其他参数时，可使用以下配置。

GRUB_CMDLINE_LINUX="lsm=lockdown,yama,integrity,apparmor,bpf"

在 Debian 和 Ubuntu 上，重新生成 GRUB 配置后重启。其他发行版请按各自的步骤操作。

sudo update-grub
sudo reboot
# 重启后执行：
cat /proc/cmdline
cat /sys/kernel/security/lsm
journalctl -u open-defender -b

确认 bpf 已启用，并检查服务日志中是否有控制器挂载错误。

事件导出

可选的导出模块通过加密的 WebSocket 协议将事件发送到 Light Defender Dashboard。没有 exporter 配置节，或将 enabled 设为 false 时，代理在本地运行。

配置方法

Dashboard 生成的配置包含代理标识符和公钥。

exporter:
  enabled: true
  endpoint_address: connector.light-defender.ru
  user_id: <Dashboard 提供的 user_id>
  config_id: <Dashboard 提供的 config_id>
  endpoint_rsa_public_key: <Dashboard 公钥，base64>
  • enabled 启用连接器。
  • endpoint_address 是 Dashboard 的 WebSocket 地址。
  • 每条消息都包含 user_id 和 config_id。
  • endpoint_rsa_public_key 是用于加密发出消息的 Dashboard 公钥。

加密

每个 WebSocket 帧都包含一个加密的 JSON 信封。消息体使用 AES-256-GCM，加密对称密钥使用 RSA-OAEP/SHA-256。

[ RSA(aes_key) ][ nonce, 12 字节 ][ ciphertext ]

代理为每次连接生成新的 RSA-2048 密钥对，并通过 system/hello 发送公钥。Dashboard 使用该密钥加密回复。代理发送的帧使用 Dashboard 公钥加密。

消息交换

代理                                 Dashboard
  |--- WebSocket 连接 --------------------->|
  |--- system/hello + 会话公钥 ------------>|
  |<-- config/set_config（30 秒内）---------|
  |--- system/ack（ok 或 error）----------->|
  |--- alert/raised（无确认）-------------->|
  |<-- config/get_config -------------------|
  |--- config/config --------------------->|
  |<-- ping（每 30 秒）---------------------|
  |--- pong ------------------------------>|

握手顺序为 hello、set_config 和 ack。握手完成后，代理会发送事件并响应配置请求。

  • system/hello 开启会话并发送代理公钥。
  • alert/raised 每个信封发送一个安全事件，无确认和自动重传。
  • config/get_config 请求当前配置，config/config 返回当前配置。
  • config/set_config 提交配置更新。导出设置和主机自身列入允许列表的地址保留在本地。
  • system/ack 返回请求状态 ok 或 error。

事件结构

{
  "version": 2,
  "task_id": 0,
  "service": "alert",
  "operation": "raised",
  "configuration_id": "...",
  "user_id": "...",
  "payload": {
    "events": [
      {
        "source": "ssh_monitor",
        "ip": "203.0.113.7",
        "message": "ssh_monitor -> found offenders ip ...",
        "happened_at": "2026-07-24T10:15:00Z",
        "details": { "engine": "syslog", "source": "/var/log/auth.log" }
      }
    ]
  }
}

source 标识生成事件的模块。资源事件还包含严重程度、指标和阈值。

超时与限制

  • 连接超时为 15 秒，每条握手消息的超时为 30 秒。
  • 读取超时为 90 秒。服务器发送 ping 时重置计时器。帧大小上限为 1 MB。
  • 重连从等待 5 秒开始，每失败一次增加 10 秒，最多等待 100 秒。连接成功后重置计数。
  • 发送队列最多容纳 1,024 个信封，超出时丢弃新事件。Dashboard 无法连接时，检测和封禁仍会继续。

远程配置发生变更时，代理会将新配置写入磁盘并重启监控模块。代理会开启新会话，并保留本地 exporter 设置及主机自身列入允许列表的地址。完整协议见 CLIENT.zh-CN.md。

命令行选项

-t、-s 和 -h 无需 root 权限。安装、更新和重启命令需要 root 权限。

用法：open-defender [选项]

选项：
  -i, --install    安装并启动 systemd 服务
  -u, --update     从 GitHub Releases 更新
  -t, --test       验证当前配置
  -s, --status     列出已启用的监控模块
  -r, --restart    重启服务
  -h, --help       显示帮助

更新

-u 从 GitHub 获取发布版本。命令根据仓库中的 version.txt 和当前安装的二进制文件，提供默认版本和架构。

sudo open-defender -u

下载成功后，更新程序替换已安装的二进制文件并重启服务。如果启动失败，会恢复之前的二进制文件。
