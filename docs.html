Quick start

Open Defender runs on Linux with systemd. Download the matching binary from GitHub Releases or let the following commands detect your architecture and place the binary in /usr/bin/open-defender.

(
  ARCH=$(uname -m)
  case "$ARCH" in
    x86_64)        ARCH=amd64 ;;
    i386|i686)     ARCH=386 ;;
    aarch64|arm64) ARCH=arm64 ;;
    armv7l)        ARCH=arm32 ;;
    *) echo "Unknown architecture: $ARCH"; exit 1 ;;
  esac
  sudo curl -fL -o /usr/bin/open-defender \
    "https://github.com/fridalif/open-defender/releases/latest/download/open-defender_$ARCH" &&
    sudo chmod +x /usr/bin/open-defender
)

Install and start the service, validate the configuration, then list the active monitors.

sudo open-defender -i
open-defender -t
open-defender -s

Service management

Use systemd to check the service, restart it, or follow its journal. sudo open-defender -r also restarts the service.

systemctl status open-defender
sudo systemctl restart open-defender
journalctl -u open-defender -f

Configuration

Agent settings live in /etc/open-defender/config.yaml. Configure the event source and thresholds for each monitor.

Monitor modes

  • blocker detects events and applies the configured blocking rule.
  • logger records matching events and lets the activity continue.
  • disabled switches the monitor off.

Main settings

  • engine selects syslog, journal, or docker.
  • log_path is the syslog file. Use unit_name for a journal unit or Docker source.
  • pattern is a regular expression with a named (?P<ip>...) group.
  • tries, window_seconds, and ban_seconds set the threshold, observation window, and ban duration.
  • ip_whitelist lists addresses that are exempt from blocking.
  • resource_monitor uses warning and alert thresholds for CPU and memory. Use zero to disable a threshold.
sudo nano /etc/open-defender/config.yaml

Run open-defender -t after editing. It reads the configuration and reports validation errors without rewriting the file.

Monitors

open-defender -s displays active monitors with their modes, engines, sources, and thresholds. Disabled monitors appear separately below the table.

/etc/open-defender/config.yaml

MONITOR           MODE     ENGINE   SOURCE                   TRIES
ssh_monitor       blocker  syslog   /var/log/auth.log        5 in 300s, ban 900s
database_monitor  logger   journal  postgresql               5 in 300s
resource_monitor  enabled  -        /var/log/open-defender/  cpu 60/90, ram 60/90

disabled: web_recon_monitor, web_brute_monitor
ssh_monitor
Detects SSH brute force from authentication logs.
web_recon_monitor
Detects reconnaissance against web applications.
web_brute_monitor
Detects brute-force attempts against web applications.
database_monitor
Detects database brute force from syslog, journal, or Docker logs.
resource_monitor
Tracks CPU and memory and reports the top consumers during overload.
network_antirecon
Detects TCP and UDP port scans with eBPF.
user_command_controller
Observes or blocks command execution through BPF LSM.

Network AntiRecon

ebpf_monitors.network_antirecon uses eBPF and XDP to detect scanning of TCP and UDP ports. A blocklisted port triggers an event immediately. Otherwise, the monitor counts distinct ports reached by a source IP during the observation window.

ebpf_monitors:
  network_antirecon:
    mode: logger
    ports_count: 10
    window_seconds: 300
    ban_seconds: 900
    whitelist_ports: [22, 80, 443]
    blacklist_ports: []

ports_count sets the distinct-port threshold, with zero disabling that check. whitelist_ports takes priority over blacklist_ports. In blocker mode, the source IP is blocked for ban_seconds. Validate and restart after changing the settings. Start with logger to see which traffic matches.

Command execution control

ebpf_monitors.user_command_controller inspects executable launches through BPF LSM. It requires BTF, active BPF LSM, and an agent running as root in the host's initial user namespace. If the controller fails to attach or update, the agent logs the error, detaches the controller and keeps the other monitors running.

This example records attempts by UID 1000 to run curl or wget.

ebpf_monitors:
  user_command_controller:
    mode: logger
    block_type: positive
    target_users_ids: ["1000"]
    target_commands: ["curl", "wget"]
  • disabled or omitting the section switches the controller off. logger allows selected attempts and emits Critical (4) events. blocker denies them with EPERM and emits High (3) events.
  • target_users_ids uses UIDs in the process's user namespace. target_commands uses executable basenames up to 63 bytes. Shell builtins without a separate execution are outside its scope.
  • When both lists are populated, the user and command must both match. An empty list leaves that criterion unrestricted. Two empty lists match nothing.
  • block_type: positive selects matches. negative selects everything else, subject to the controller's exclusions.

Root is excluded, including real or effective UID 0 on the host or in a container's user namespace. A logger event reports an attempt to execute a command.

Attempts in unknown user or mount namespaces pass through without events. The agent discovers namespaces before attaching and every 150 seconds thereafter, then waits another 150 seconds for each namespace to become ready. The policy activates when both namespaces are ready.

Validate the configuration and check the journal after restarting.

open-defender -t
sudo open-defender -r
journalctl -u open-defender -f

Enable BPF LSM with GRUB

Check whether the kernel supports BPF LSM and whether it is active. A missing LSM file can mean that securityfs is unmounted or that LSM information is unavailable.

cat /sys/kernel/security/lsm
cat /proc/cmdline
grep CONFIG_BPF_LSM /boot/config-$(uname -r)

If bpf already appears in the active list, GRUB needs no changes. The kernel must have CONFIG_BPF_LSM=y. Use your distribution's instructions if the kernel configuration is stored elsewhere.

Back up the GRUB settings and confirm access to a recovery console. Check /etc/default/grub and /etc/default/grub.d/. If lsm= is already present, append bpf to that list. Otherwise, add one lsm= option to GRUB_CMDLINE_LINUX using the current list from /sys/kernel/security/lsm plus bpf. Keep the other kernel options.

For example, if the active list contains lockdown,yama,integrity,apparmor and this variable has no other options:

GRUB_CMDLINE_LINUX="lsm=lockdown,yama,integrity,apparmor,bpf"

On Debian and Ubuntu, rebuild the GRUB configuration and reboot. Use the corresponding procedure for your distribution.

sudo update-grub
sudo reboot
# After reboot:
cat /proc/cmdline
cat /sys/kernel/security/lsm
journalctl -u open-defender -b

Confirm that bpf is active and check the service journal for attachment errors.

Event export

The optional exporter sends events to Light Defender Dashboard using an encrypted protocol over WebSocket. The agent works locally when the exporter section is absent or enabled is set to false.

Setup

Dashboard provides the agent identifiers and public key in the generated configuration.

exporter:
  enabled: true
  endpoint_address: connector.light-defender.ru
  user_id: <your Dashboard user_id>
  config_id: <your Dashboard config_id>
  endpoint_rsa_public_key: <Dashboard public key, base64>
  • enabled activates the connector.
  • endpoint_address is the Dashboard WebSocket endpoint.
  • user_id and config_id are included in each message.
  • endpoint_rsa_public_key is the Dashboard key used to encrypt outbound messages.

Encryption

Each WebSocket frame carries an encrypted JSON envelope. The body uses AES-256-GCM and the symmetric key uses RSA-OAEP/SHA-256.

[ RSA(aes_key) ][ nonce, 12 bytes ][ ciphertext ]

The agent creates a new RSA-2048 key pair for each connection and provides its public key in system/hello. Dashboard uses that key for replies. The agent uses the Dashboard public key for outbound frames.

Message exchange

Agent                                Dashboard
  |--- WebSocket connection -------------->|
  |--- system/hello + session public key ->|
  |<-- config/set_config (within 30 s) ------|
  |--- system/ack (ok or error) ----------->|
  |--- alert/raised (no acknowledgment) -->|
  |<-- config/get_config -------------------|
  |--- config/config --------------------->|
  |<-- ping (every 30 s) --------------------|
  |--- pong ------------------------------>|

The handshake runs in order: hello, set_config, ack. The agent then sends events and responds to configuration requests.

  • system/hello opens a session and sends the agent's public key.
  • alert/raised sends one security event per envelope, without acknowledgment or automatic replay.
  • config/get_config requests the current configuration. config/config returns it.
  • config/set_config submits a configuration update. The export settings and the host's own allowlisted addresses stay local.
  • system/ack reports ok or error for the request.

Event structure

{
  "version": 2,
  "task_id": 0,
  "service": "alert",
  "operation": "raised",
  "configuration_id": "...",
  "user_id": "...",
  "payload": {
    "events": [
      {
        "source": "ssh_monitor",
        "ip": "203.0.113.7",
        "message": "ssh_monitor -> found offenders ip ...",
        "happened_at": "2026-07-24T10:15:00Z",
        "details": { "engine": "syslog", "source": "/var/log/auth.log" }
      }
    ]
  }
}

source identifies the monitor that emitted an event. Resource events also carry a severity, metric, and threshold.

Timing and limits

  • Connection timeout is 15 seconds. Handshake messages have a 30-second timeout.
  • Read timeout is 90 seconds and resets on each server ping. The frame size limit is 1 MB.
  • Reconnect starts after 5 seconds and adds 10 seconds per failure, up to 100 seconds. A successful connection resets the counter.
  • The outgoing queue holds 1,024 envelopes and discards overflow. Detection and blocking continue when Dashboard is unreachable.

A changed remote configuration is written to disk and restarts the monitors. The agent opens a new session and retains the local exporter settings and its own allowlisted addresses. See CLIENT.md for the full protocol.

CLI commands

-t, -s, and -h can run without root privileges. The installation, update, and restart commands require root.

Usage: open-defender [options]

Options:
  -i, --install    Install and start the systemd service
  -u, --update     Update from GitHub Releases
  -t, --test       Validate the current configuration
  -s, --status     List active monitors
  -r, --restart    Restart the service
  -h, --help       Show help

Updates

-u fetches a GitHub release. The command proposes a version from version.txt in the repository and an architecture based on the installed binary.

sudo open-defender -u

Once downloaded, the binary replaces the installed one and the service restarts. If startup fails, the updater restores the previous binary.
